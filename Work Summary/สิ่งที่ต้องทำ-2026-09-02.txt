B) ปัญหาประสิทธิภาพ — ทำก่อนคนใช้เยอะ
================================================================

  (B1) ลด N+1 round-trip ในเส้นทาง To-do                [ทำแล้ว 2 ก.ย. (บางส่วน)]
       วัดจริงตอนพบ (หักค่าล็อกอินออกแล้ว): แตกงาน 5 ขั้นตอน = 48 queries
       ต้นเหตุที่แก้แล้ว: lib/taskCalendar.ts -> syncAllSubtaskEvents()
         เดิมวนเรียก syncSubtaskEvent() ทีละขั้นตอน แล้วข้างในไปเช็ค
         ensureTaskCategory() (หมวดหมู่เดียวกันทุกรอบ) และ dropParentEvent()
         (parent eventถูกลบไปตั้งแต่รอบแรก รอบหลังๆ คือ query เปล่า) ซ้ำอีก N-1 ครั้ง
       แก้: แยก syncSubtaskEventCore() รับ categoryId/skipDropParent จากภายนอก
         syncAllSubtaskEvents() คำนวณ category + drop parent ครั้งเดียวก่อนเข้าลูป
       ผลวัดจริงหลังแก้: แตกงาน 5 ขั้นตอน 48 -> 34 queries (ลด ~30%)
       ยังไม่ทำ (ของเดิมที่เสนอไว้ ไม่คุ้มทำต่อตอนนี้):
         - createMany สร้าง subtask รอบเดียวแทน create ทีละตัวใน for loop
         - ยุบ findUnique(Subtask+Task) ที่ยังทำซ้ำต่อขั้นตอนใน syncSubtaskEventCore
         เหตุผลที่พักไว้: เวลาที่เหลือส่วนใหญ่ตอนนี้คือ Gemini API latency (~4s)
         ไม่ใช่ query เพิ่มอีก 6 คิว จึงไม่คุ้มความเสี่ยงรื้อ API เดิม

  (B2) เพิ่ม index ที่ขาด 2 ตัว                          [ทำแล้ว 2 ก.ย.]
       Subtask.taskId   — เพิ่ม @@index([taskId]) แล้ว
       Category.userId  — เพิ่ม @@index([userId]) แล้ว
       (Seq Scan ยังเลือกใช้ที่ขนาดข้อมูลปัจจุบัน เพราะตารางเล็ก ปกติ — index
       พร้อมรองรับตอนข้อมูลโตแล้ว ไม่ต้องกลับมาแก้อีกทีตอนนั้น)

  (B3) ใส่ rate limit — โดยเฉพาะปุ่มที่เรียก AI          [ยังไม่ทำ]  ~30 นาที
       grep ทั้งโปรเจกต์: ไม่มี rate limit / throttle ที่ไหนเลย
       เสี่ยง : ใครก็กด "แยกงาน" รัวๆ ได้ -> Gemini quota หมด / ค่าใช้จ่ายบาน
                และคนอื่นใช้ไม่ได้ตาม
       เส้นที่ต้องคุมก่อน : /api/tasks/[id]/breakdown, /api/chat,
                            /api/ai/*, /api/groups/[id]/distribute
       ยังไม่มี cache หรือคิวสำหรับ Gemini ด้วย

  (B4) ใส่ pagination / ตัวกรองช่วงวัน                   [ยังไม่ทำ]  ~30 นาที
       GET /api/events ดึง event ทั้งหมดตั้งแต่ใช้แอปมา ไม่มีตัวกรองวันเลย
       GET /api/tasks  ดึงงานทั้งหมดพร้อม subtask + scheduledEvent
       ผู้ใช้ที่ใช้ 2 ปี (~2,000 event) จะโหลดทั้งหมดทุกครั้งที่เปิดปฏิทิน
       ยังไม่เร่ง แต่จะเป็นปัญหาแน่เมื่อข้อมูลสะสม

  (B5) ลดน้ำหนักหน้าแรก                                  [ยังไม่ทำ]  ~20 นาที
       ผู้ใช้ใหม่โหลด ~1.08 MB (ยังไม่รวม JS bundle):
           652 KB  eddy-duo-wave.webm  (มาสคอต)
           250 KB  eddy-duo-wave-still.png (poster — โหลดทั้งที่ดูวิดีโออยู่แล้ว)
           151 KB  eddy-logo (srcset ~384w)
            23 KB  eddy-a-128.png
       ~1.05 GB/วัน ต่อผู้ใช้ 1,000 คน (~31 GB/เดือน)
       ทางลัด : ย่อ/ตัด poster ออก ลดได้ ~250KB ทันที
