================================================================
สรุปการทำงานของระบบ EDDY (ผู้ช่วยจัดตารางชีวิตด้วย AI)
ตั้งแต่รับข้อมูลผู้ใช้ → การวิเคราะห์ของ AI → การแสดงผล + APIs
อัปเดต: 13 สิงหาคม 2569
================================================================

ไฟล์นี้อธิบาย "ภาพรวมการไหลของข้อมูล" ทั้งระบบ: ผู้ใช้ป้อนอะไรเข้ามา,
ระบบเก็บที่ไหน, AI ใช้ข้อมูลและหลักการอะไรวิเคราะห์, แล้วแสดงผลกลับ
ให้ผู้ใช้อย่างไร พร้อมรายการ API ทั้งหมดว่าดึง/เขียนข้อมูลจากแหล่งไหน


================================================================
0) เทคโนโลยีหลัก (Tech Stack)
================================================================
- Next.js 14 (App Router) + React 18 + TypeScript  → ทั้งหน้าเว็บและ API
  (Route Handlers ใต้ app/api/**) อยู่ในโปรเจกต์เดียว
- Prisma ORM + PostgreSQL บน Neon (คลาวด์)          → ฐานข้อมูลหลัก
- NextAuth v5 (Auth.js): Credentials + Google OAuth  → ระบบล็อกอิน
- Google Gemini API (โมเดล gemini-flash-lite-latest) → สมอง AI จริง
- Google Calendar API v3 (อ่านอย่างเดียว)            → ดึงปฏิทิน Google
- Tailwind CSS + framer-motion + lucide-react        → UI/ดีไซน์

สถาปัตยกรรมสำคัญ = "ไฮบริด AI":
  • LLM (Gemini) ตัดสินเรื่องที่ต้องใช้ภาษา/การตีความ = "ใคร / อะไร / หมวดไหน"
  • อัลกอริทึม local (โค้ดธรรมดา ไม่เรียก AI) คำนวณเรื่องตัวเลข = "เมื่อไหร่ / ว่างไหม / สำคัญแค่ไหน"
  เหตุผล: การวางเวลาต้องการันตีว่า "ไม่ชนกันจริง" → ใช้คณิตศาสตร์ ไม่ปล่อยให้ AI เดา
  และถ้า AI ล่ม/ไม่มี key ระบบยังทำงานต่อได้ด้วย local ล้วน (fallback)


================================================================
1) การรับข้อมูลจากผู้ใช้ (Input) — เข้าระบบทางไหนบ้าง
================================================================
(1.1) สมัคร/เข้าสู่ระบบ
   - สมัคร: username(ชื่อแสดง) + email + password  → POST /api/auth/register
   - เข้าสู่ระบบด้วย email/password หรือ Google OAuth → NextAuth
(1.2) Onboarding (ครั้งแรก) → เลือก "บทบาท": นักเรียน / นักศึกษา / วัยทำงาน
   - ใช้กำหนดหมวดหมู่เริ่มต้น + ปรับภาษา/บริบทของ AI (ดูข้อ 4.2)
(1.3) โปรไฟล์ → ชื่อ, @username, รูป/อีโมจิ/สีอวาตาร์, "เกี่ยวกับฉัน/นิสัย" (bio),
   ช่วงเวลาที่สะดวก (dayStart–dayEnd) + โซนเวลา
   → bio + เวลาสะดวก เป็น "อาหารสมอง" ให้ AI วิเคราะห์เฉพาะตัว
(1.4) ปฏิทิน → เพิ่ม/แก้กิจกรรม (ชื่อ, วัน, เวลาเริ่ม-จบ, หมวด, สถานที่, รายละเอียด)
   - คลิกช่องเวลาว่างเพื่อเพิ่ม, ลากดูสัปดาห์/เดือน/วัน
(1.5) Loop ชีวิต (ตารางประจำ) → กิจกรรมซ้ำทุกสัปดาห์ (วิชาเรียน/เวลาทำงาน)
   ระบุ วัน(หลายวัน) + เวลา + หมวด + ใช้ถึงวันไหน (เช่น สิ้นเทอม)
(1.6) สิ่งที่ต้องทำ (To-do) → ชื่องาน + ความสำคัญ(สูง/กลาง/ต่ำ) + กำหนดส่ง + เวลาโดยประมาณ
   - แตกงานย่อยเอง หรือให้ AI แตกให้ (subtask)
(1.7) แชทกับเอ็ดดี้ (ChatWidget) → พิมพ์ภาษาธรรมชาติ เช่น "พรุ่งนี้บ่าย 2 นัดหมอ"
(1.8) กลุ่ม → สร้างกลุ่ม, เชิญเพื่อน, เพิ่มงานกลุ่ม, กดให้ AI กระจายงาน
(1.9) เชื่อม Google Calendar → ดึงกิจกรรมจากปฏิทิน Google มาแสดงรวม (อ่านอย่างเดียว)


================================================================
2) ชั้นข้อมูล (ข้อมูลถูกเก็บ/ดึงมาจากไหน)
================================================================
(2.1) ฐานข้อมูลหลัก = PostgreSQL บน Neon (ผ่าน Prisma) — ตาราง (model):
   • User                → บัญชี + โปรไฟล์ (name, bio, role, dayStart/dayEnd, timezone, avatar…)
   • Account / Session / VerificationToken → ข้อมูล NextAuth (รวม token ของ Google)
   • Category            → หมวดหมู่ปฏิทินของผู้ใช้ (ชื่อ+สี)
   • Event               → กิจกรรมในปฏิทิน (วัน, เวลา, หมวด, สถานที่)
   • RecurringEvent      → "Loop ชีวิต" ตารางประจำ (days, เวลา, endDate)
   • Task / Subtask      → สิ่งที่ต้องทำ + งานย่อย
   • Group / GroupMember → กลุ่ม + สมาชิก(สถานะ invited/accepted, บทบาท owner/member)
   • GroupTask / GroupTaskAssignment → งานกลุ่ม + การมอบหมาย (suggested/approved)
   • ChatMessage         → ประวัติแชท (ถ้าเก็บ)

(2.2) แหล่งข้อมูลภายนอก (External)
   • Google Gemini API      → คำตอบ/ผลวิเคราะห์ของ AI (ไม่เก็บถาวร ดึงสด)
   • Google Calendar API v3 → กิจกรรมจากปฏิทิน Google ของผู้ใช้ (ดึงสด, อ่านอย่างเดียว)
   ทั้งคู่ต้องมีคีย์ใน .env / .env.local (ไม่ commit ขึ้น git):
   GEMINI_API_KEY, DATABASE_URL(Neon), AUTH_SECRET, AUTH_GOOGLE_ID, AUTH_GOOGLE_SECRET

3) หลักการทำงานของ AI ในระบบ (ภาพรวม)
================================================================
สมอง AI ทั้งหมดอยู่ที่ lib/gemini.ts เรียก Gemini รุ่น "gemini-flash-lite-latest"
(เลือกรุ่น lite เพราะตอบเร็ว ~1 วิ เทียบรุ่นเต็มที่ "คิดก่อนตอบ" ~30 วิ ซึ่งเกินจำเป็น)

รูปแบบการเรียกมี 2 แบบ:
   (ก) ข้อความอิสระ (askEddy / generateWeeklySummary) → ได้ข้อความภาษาไทยกลับมา
   (ข) Structured Output (callGeminiJSON) → บังคับให้ตอบเป็น JSON ตาม schema
       ใช้กับงานที่ต้องเอาผลไปใช้ต่อ (แยกข้อความ, วิเคราะห์ตาราง, แตกงาน, กระจายงาน)

*** สิ่งที่ทุกฟังก์ชันของ AI ได้รับเป็น "บริบท" เสมอ (ทำให้คำตอบเฉพาะตัว) ***
   buildUserProfileContext(user) รวม 3 อย่าง:
     1. ROLE_AI_CONTEXT[role] — บริบทตามวัย (ดูข้อ 4.2)
     2. bio — "นิสัย/ตัวตน" ที่ผู้ใช้กรอกในโปรไฟล์
     3. dayStart–dayEnd — ช่วงเวลาที่สะดวกทำงาน
   → AI เอาไปปรับ "ภาษา" และ "เวลาที่แนะนำ" ให้เข้ากับแต่ละคน

*** ถ้าไม่มี GEMINI_API_KEY หรือเรียกไม่สำเร็จ → คืน null แล้ว caller สลับไปใช้
    อัลกอริทึม local ใน lib/aiMock.ts แทน (แอปไม่พังเพราะ AI ล่ม) ***

4) ความสามารถของ AI ทีละอย่าง (input → หลักการ → output)
================================================================

(4.1) แชท + Quick-add: แปลงข้อความเป็นกิจกรรม/งาน   [API: POST /api/chat]
   ข้อมูลที่ป้อนให้ AI: ข้อความผู้ใช้ + วันนี้(เวลาไทย) + รายชื่อหมวดหมู่ +
                       โปรไฟล์(role/bio/เวลาสะดวก) + งาน/กิจกรรมล่าสุด 5 รายการ
   ทำ 2 อย่างขนานกัน:
     • askEddy() → ข้อความตอบกลับเป็นกันเอง
     • parseMessageToEvent() → JSON { intent: event|task|none, title, date, startTime, categoryId }
       AI ตีความวัน/เวลาแบบภาษาคน ("พรุ่งนี้", "ศุกร์หน้า") ให้เป็น YYYY-MM-DD / HH:mm
       และเดาหมวดหมู่ที่เหมาะจากรายชื่อที่ให้
   Fallback: ถ้า AI ไม่ตอบ → parseEventFromText() (lib/aiMock) ใช้ regex จับวัน/เวลาแบบง่าย
   แสดงผล: ถ้าได้ draft → เปิดฟอร์มเพิ่มกิจกรรมที่กรอกไว้ให้แล้ว ผู้ใช้แค่กดยืนยัน

(4.2) บทบาท (Role) ปรับ AI ให้เข้ากับวัย   [lib/roles.ts]
   3 บทบาท → กำหนด (ก)หมวดหมู่เริ่มต้น (ข)บริบทให้ AI:
     • นักเรียน (school)  : ภาษาเป็นกันเอง ให้กำลังใจ; รู้ว่ามีสอบกลาง/ปลายภาค การบ้านหนัก
     • นักศึกษา (university): รู้ว่ามี midterm/final งานกลุ่ม ตารางยืดหยุ่น; กระตุ้นวางแผนล่วงหน้า
     • วัยทำงาน (working)  : ภาษาสุภาพ กระชับ มืออาชีพ; เน้นงาน/ประชุม/เดดไลน์/work-life balance

(4.3) วิเคราะห์ตารางตอนเพิ่มกิจกรรม   [API: POST /api/ai/analyze-event]
   ป้อน: กิจกรรมใหม่ + กิจกรรมอื่นในวันเดียวกัน + หมวดหมู่ + โปรไฟล์ผู้ใช้
   AI ตอบ JSON: hasConflict(ชนไหม), densityLevel(ว่าง/ปกติ/ค่อนข้างแน่น/แน่นมาก),
                message(คำแนะนำ), suggestedStart/End(เวลาแนะนำถ้าชน)
   Fallback: ตรวจเวลาชนแบบคำนวณช่วงเวลา (aiMock)

(4.4) สรุปภาพรวมสัปดาห์   [API: POST /api/ai/weekly-summary]
   ป้อน: รายการกิจกรรมทั้งสัปดาห์ + หมวดหมู่ + โปรไฟล์
   AI ตอบ: ข้อความ 1–2 ประโยค (สัปดาห์นี้แน่นแค่ไหน วันไหนหนัก หมวดไหนเยอะ + ให้กำลังใจ)
   Fallback: buildWeeklySummary() คำนวณสถิติเองแบบ local
   แสดงผล: การ์ด/Popover "สรุปสัปดาห์" ในหน้าปฏิทิน

(4.5) แตกงานใหญ่เป็นงานย่อย   [API: POST /api/tasks/[id]/breakdown]
   ป้อน: ชื่องาน (+รายละเอียด) → AI ตอบเป็น array ของ subtask 3–6 ข้อ
   เรียงตามลำดับที่ควรทำ เริ่มด้วยคำกริยา → บันทึกเป็น Subtask ในหน้า To-do

(4.6) กระจายงานกลุ่มให้สมาชิก (ไฮบริดชัดสุด)   [API: POST /api/groups/[id]/distribute]
   นี่คือหัวใจของหลักการ "AI ตัดสินใคร, local คำนวณเมื่อไหร่":
   ขั้นที่ 1 (local) คำนวณ "เวลาว่าง" ของสมาชิกแต่ละคนใน 7 วันข้างหน้า
       - รวม "เวลาไม่ว่าง" = Event ในปฏิทิน + Loop ประจำ(ขยายเป็นวันจริง)
       - หักออกจากกรอบเวลาที่สะดวก (dayStart–dayEnd) → ได้ช่วงว่าง (computeFreeSlots)
       - ตัดเวลาที่ผ่านมาแล้วของวันนี้ทิ้ง (ไม่เสนอเวลาย้อนหลัง)
   ขั้นที่ 2 (AI) ให้ Gemini เลือก "ใครควรทำงานไหน"
       - ป้อน: งาน(ชื่อ/เวลาที่ใช้/เดดไลน์) + สมาชิก(ชื่อ/เวลาว่างรวม/นิสัย bio)
       - หลักการ: กระจายให้เป็นธรรม คนว่างมากรับมากกว่า จับคู่ให้เข้ากับนิสัย
   ขั้นที่ 3 (local) วางเวลาจริงลงช่องว่าง (placeTask)
       - เรียงงาน: ใกล้เดดไลน์ก่อน แล้วงานยาวก่อน
       - ผู้สมัคร: คนที่ AI เลือกก่อน ถ้าไม่พอค่อยไล่คนที่ว่างมากสุด (load balance)
       - การันตีไม่ทับกัน + ไม่เกินเดดไลน์ → บันทึกเป็น GroupTaskAssignment (status=suggested)
   ถ้า Gemini ล่ม/ไม่มี key → ข้ามขั้น 2 ใช้ local ล้วน (usedAI=false)

5) อัลกอริทึม local สำคัญ (ไม่เรียก AI — คำนวณล้วน)
================================================================

(5.1) Priority Score — จัดลำดับ "ควรทำงานไหนก่อน"   [lib/priorityScore.ts]
   หลักการคล้าย Eisenhower Matrix ผสม weighted scoring จาก 3 แกน:
     • importance (ความสำคัญ)  : สูง=1.0, กลาง=0.6, ต่ำ=0.3       น้ำหนัก 0.50
     • urgency (ความเร่งด่วน)   : จาก dueDate = clamp(1 − วันเหลือ/14, 0..1)
                                  ไม่มีกำหนดส่ง=0.3, เลยกำหนด=1.0   น้ำหนัก 0.35
     • effort (ความยาว/ง่าย)    : งานสั้นได้คะแนนสูง = 1 − นาที/240  น้ำหนัก 0.15
   คะแนนรวม = importance*0.5 + urgency*0.35 + effort*0.15
   คำนวณสดทุกครั้ง (ไม่เก็บ DB) เพราะ urgency เปลี่ยนทุกวัน
   ใช้ที่: ปุ่ม "เรียงตาม AI แนะนำ" + ป้าย "ควรทำก่อน" ในหน้า To-do

(5.2) Free-time / วางงาน   [lib/freeTime.ts]
   - computeFreeSlots: เอากรอบเวลาสะดวก − ช่วงไม่ว่าง(รวมทับกันก่อน) = ช่วงว่างต่อวัน
   - placeTask: วางงานลงช่องว่างแรกที่พอ (แบบ first-fit) ก่อนเดดไลน์ แล้วตัดเวลาที่ใช้ทิ้ง
   - default กรอบ 08:00–22:00 ถ้าผู้ใช้ไม่ได้ตั้ง

(5.3) ขยาย Loop ประจำเป็นกิจกรรมจริง   [lib/recurring.ts]
   RecurringEvent (days="1,3,5") → กางออกเป็น Event ของแต่ละวันที่ตรงในช่วงที่ดู
   ใช้ทั้งการแสดงบนปฏิทิน และการคิดเวลาไม่ว่างตอนกระจายงานกลุ่ม


================================================================
6) รายการ API ทั้งหมด — ดึง/เขียนข้อมูลจากไหน
================================================================
สัญลักษณ์แหล่งข้อมูล:  [DB]=Neon/Prisma  [AI]=Gemini  [G]=Google Calendar  [Auth]=NextAuth

— ระบบบัญชี —
  POST /api/auth/register              สร้างผู้ใช้ (แฮชรหัสผ่าน)                      [DB]
  /api/auth/[...nextauth]              ล็อกอิน/ออก/เซสชัน (Credentials+Google)        [Auth][DB]
  POST /api/onboarding                 บันทึกบทบาท + สร้างหมวดหมู่เริ่มต้น            [DB]
  GET/PATCH /api/profile               อ่าน/แก้โปรไฟล์ (ชื่อ,bio,เวลาสะดวก,avatar)     [DB]

— ปฏิทิน / หมวดหมู่ / Loop —
  GET/POST /api/categories             รายการ/เพิ่มหมวดหมู่                            [DB]
  PATCH/DELETE /api/categories/[id]    แก้/ลบหมวดหมู่                                  [DB]
  GET/POST /api/events                 รายการ/เพิ่มกิจกรรม                            [DB]
  PATCH/DELETE /api/events/[id]        แก้/ลบกิจกรรม                                  [DB]
  GET/POST /api/recurring              รายการ/เพิ่ม Loop ประจำ                        [DB]
  PATCH/DELETE /api/recurring/[id]     แก้/ลบ Loop                                    [DB]
  GET /api/google/calendar             ดึงกิจกรรมจากปฏิทิน Google (อ่านอย่างเดียว)    [G][DB(token)]

— สิ่งที่ต้องทำ (To-do) —
  GET/POST /api/tasks                  รายการ/เพิ่มงาน                               [DB]
  PATCH/DELETE /api/tasks/[id]         แก้(เสร็จ/แก้)/ลบงาน                           [DB]
  GET/POST /api/tasks/[id]/subtasks    รายการ/เพิ่มงานย่อย                           [DB]
  PATCH /api/tasks/[id]/subtasks/reorder  จัดลำดับงานย่อย (ลากสลับ)                   [DB]
  POST /api/tasks/[id]/breakdown       ให้ AI แตกงานเป็นงานย่อย                        [AI][DB]
  PATCH/DELETE /api/subtasks/[id]      แก้/ลบงานย่อย                                  [DB]

— AI ผู้ช่วย —
  POST /api/chat                       แชท + แปลงข้อความเป็นกิจกรรม/งาน                [AI][DB]
  POST /api/ai/analyze-event           วิเคราะห์ตาราง/เวลาชนตอนเพิ่มกิจกรรม           [AI][DB]
  POST /api/ai/weekly-summary          สรุปภาพรวมสัปดาห์                              [AI][DB]

— กลุ่ม (Collaboration) —

7) ตัวอย่างการไหลของข้อมูลแบบครบวงจร (End-to-End)
================================================================
ตัวอย่าง A — พิมพ์ในแชท "พรุ่งนี้ 14:00 นัดหมอฟัน"
  ผู้ใช้พิมพ์ → POST /api/chat → ดึงหมวดหมู่+โปรไฟล์+งานล่าสุด [DB]
  → Gemini แปลงเป็น {intent:event, title:"นัดหมอฟัน", date:พรุ่งนี้, startTime:14:00} [AI]
  → คืน draft → หน้าเว็บเปิดฟอร์มเพิ่มกิจกรรมที่กรอกไว้แล้ว → ผู้ใช้กดยืนยัน
  → POST /api/events บันทึกลง [DB] → แสดงบนปฏิทินทันที

ตัวอย่าง B — กดปุ่ม "ให้เอ็ดดี้จัดงานกลุ่ม"
  POST /api/groups/[id]/distribute
  → [DB] ดึงสมาชิก+โปรไฟล์, งานกลุ่ม, Event+Loop ของสมาชิก(7วัน)
  → [local] คำนวณช่วงว่างแต่ละคน (computeFreeSlots)
  → [AI] Gemini เลือกใครทำงานไหน (จากเวลาว่าง+นิสัย)
  → [local] วางเวลาจริงไม่ให้ชน (placeTask) → บันทึก assignment (suggested) [DB]
  → แสดงผลการมอบหมายให้สมาชิกกด "ยืนยัน" → กลายเป็น Event ในปฏิทินตัวเอง

8) การแสดงผลให้ผู้ใช้ (Output / หน้าจอหลัก)
================================================================
  • Dashboard  : การ์ดโฟกัสวันนี้, สถิติงาน/ความคืบหน้า, มินิปฏิทิน, ตารางสัปดาห์, กิจกรรมที่จะถึง

  • To-do      : รายการงาน+งานย่อย, เรียงตาม AI แนะนำ(Priority Score), แตกงานด้วย AI

  ฟอนต์ IBM Plex Sans Thai + สเกลตัวอักษรมาตรฐาน

9) สรุปหลักคิดของระบบ (Design Principles) ในหนึ่งย่อหน้า
================================================================
EDDY รับข้อมูลผู้ใช้จากหลายทาง (โปรไฟล์/ปฏิทิน/งาน/แชท/กลุ่ม) เก็บลง Postgres(Neon).
เมื่อต้องใช้ "การตีความภาษา/การตัดสินใจเชิงคน" (แปลงข้อความ, แนะนำ, เลือกคนทำงาน,
แตกงาน, สรุป) จะส่งบริบท—โดยเฉพาะบทบาท+นิสัย(bio)+เวลาสะดวก—ให้ Gemini วิเคราะห์.
ส่วนงานที่ต้อง "ถูกต้องแม่นยำเชิงตัวเลข" (เวลาว่าง, ไม่ให้ชน, จัดลำดับความสำคัญ)
ใช้อัลกอริทึม local ที่คำนวณเอง. ทั้งสองส่วนทำงานร่วมกันแบบไฮบริด และมี fallback
เป็น local เสมอเมื่อ AI ไม่พร้อม เพื่อให้ระบบเสถียรและใช้งานได้ตลอด.
